1. The Problem We Are Solving
Misinformation spreads rapidly on social media across India, particularly in vernacular languages.
A false claim posted on WhatsApp or Twitter in Hindi or Tamil can reach millions of people within
hours. Human fact-checkers cannot possibly keep up with the volume of content — there are
simply too many posts and too few reviewers.
Existing AI fact-checking solutions face two critical problems:
•

They are too slow — LLM-based verification takes seconds per item, which does not scale
to millions of posts per day.

•

They are too expensive — running every post through an LLM costs too much at scale.

•

They get confused — retrieval systems return outdated or conflicting facts, leading to
wrong verdicts.

1.1 The Core Challenge
Key Constraint 1 — Throughput
The system must process at least 5,000 posts per minute at peak load. A single LLM call takes 2-10
seconds. You cannot call the LLM for every post.

Key Constraint 2 — Context Accuracy
When retrieving verified facts, the system must not get confused by outdated or conflicting data in the
facts database. A 2019 fact about a vaccine may directly contradict a 2024 fact about the same topic.

1.2 The Core Insight — Tiered Processing
The solution is a tiered pipeline. Instead of treating every post the same, we use cheap fast filters
to eliminate most volume before reaching expensive LLM calls. About 60% of posts contain no
verifiable factual claim at all — they are opinions, jokes, or questions. These are dropped cheaply
at Tier 1. Of the remaining 40%, most can be auto-verified by matching against the facts database
at Tier 2. Only 5-10% of total posts ever reach the expensive LLM tier. This keeps costs
manageable while maintaining high accuracy.

2. System Architecture — VeriCheck Pipeline
VeriCheck is a five-tier processing pipeline. Every post enters at Tier 0 and flows downward. Each
tier is progressively more expensive but handles progressively less volume. The architecture is
the primary mechanism for achieving both the throughput constraint and the cost constraint
simultaneously.

2.2 What Happens at Each Tier
Tier 0 — Ingestion
Posts arrive from social media platforms and news sites via web scrapers and MCP connectors.
Every post is immediately published to a Kafka topic called raw-posts. Kafka acts as a durable
buffer — if any downstream service crashes, no posts are lost, and processing resumes from
where it stopped. This is the entry point for 100% of all content.

Tier 1 — Pre-filter (the volume killer)
Three fast operations run on every post in under 5ms total:
1. Language detection using fastText — identifies which of the 8 supported Indian languages
the post is written in. Unsupported languages are archived without further processing.
2. Claim extraction using spaCy NER with custom rules — identifies whether the post
contains a verifiable factual claim. Opinions ('I think the PM is wrong'), jokes, and
questions are dropped here. This eliminates approximately 60% of total volume.
3. Duplicate detection using MinHash — suppresses re-processing of posts that are nearidentical to posts already in the pipeline. Prevents redundant work when the same claim
goes viral.

Tier 2 — Hybrid Retrieval and Ranking
For posts that contain a real factual claim, the system searches the verified facts database using
two methods simultaneously:
•

BM25 keyword retrieval — finds facts that share specific keywords with the claim. Fast
and precise for exact matches.
• FAISS dense vector retrieval — finds facts that are semantically similar even if they use
different words. Handles paraphrasing and synonyms.
The top results from both methods are merged and then re-scored by a cross-encoder reranker.
The reranker is the key to solving the context accuracy problem — it jointly scores each (claim,
candidate fact) pair and applies penalties to facts that are outdated or from lower-authority
sources. The reranker produces a confidence score. If the score is above a configured threshold,
the post is auto-flagged and a verdict is generated without needing the LLM.

Tier 3 — LLM Reasoning (only 5-10% of posts)
Posts where the reranker confidence is below the threshold — meaning the system is genuinely
uncertain — are sent to the LLM tier. The LLM receives a structured prompt containing the
original claim, the top 3 retrieved facts from the database, and the language context. It returns a
structured JSON verdict with a label, confidence score, evidence IDs, and a plain-language
explanation. LLM calls use the batch API to minimize cost.

Output Layer
Verdicts flow to three destinations based on confidence level. High-confidence verdicts appear on
the reviewer dashboard within 10 seconds. Low-confidence verdicts enter a human review queue.
All verdicts are also available via a REST API and webhooks for third-party integrations. Human
corrections from the review queue feed back into the verified facts database, continuously
improving the system.

3. What is Kafka and Why We Use It
Apache Kafka is a distributed event streaming platform — essentially a very fast, durable
message queue that sits between systems that produce data and systems that consume it. It was
originally built by LinkedIn and is now open-source through the Apache Foundation.

3.1 The Mental Model
Think of Kafka as a conveyor belt at a factory. Multiple machines (your scrapers) drop items onto
the belt. Multiple workstations (your pipeline workers) pick items off the belt to process them.
Each workstation works at its own speed. Items are not removed from the belt until every
workstation that needs them has processed them. And crucially — if one workstation breaks
down, the belt keeps running, and that station can resume from exactly where it stopped once it is
fixed.

3.3 Why Kafka Solves Your Throughput Problem
•

Horizontal scaling: add more consumer workers to handle more volume instantly, with no
code changes.

•

Fault tolerance: if the LLM service goes down, Kafka holds all messages. Nothing is lost.
Workers resume when the service recovers.

•

Multiple independent consumers: your Tier 1 filter and your analytics logger both read the
same topic at their own pace without interfering with each other.
Replay: you can reprocess old posts with a new model version by rewinding the consumer
offset.

4. Web MCPs in VeriCheck
MCP stands for Model Context Protocol — an open standard published by Anthropic that allows
AI agents to call external tools (web scrapers, browsers, databases, APIs) as easily as calling a
Python function. A Web MCP server wraps web browsing and scraping capability into a tool your
pipeline can invoke directly.

4.1 Where MCPs Fit in the Pipeline
Place 1 — Ingestion Layer (replacing custom scrapers)
Traditional web scrapers are brittle — they break whenever a news site changes its HTML
structure, which happens constantly. Web MCPs solve this problem. Instead of maintaining CSS
selectors and XPath expressions for every site, you describe what you want in natural language
and the MCP handles the rest, including JavaScript rendering, CAPTCHA bypass (for paid
MCPs), and clean content extraction.

Place 2 — Live Fact Sourcing (keeping the database current)
When Tier 2 retrieval finds no high-confidence matching fact in the database, instead of
immediately returning UNVERIFIABLE, the system can trigger a Web MCP to search trusted
sources like PIB (Press Information Bureau), WHO, AltNews, or FactCheck.in in real time. The
retrieved content is parsed, embedded, and stored in the facts database. This means the
database grows automatically as new claims appear, without requiring manual curation.

10. Key Design Decisions Explained
Decision

What we chose

Why

Why hybrid retrieval?

BM25 + FAISS together

BM25 is precise for keywords; FAISS handles
paraphrasing. Together they have higher recall
than either alone.

Why a cross-encoder
reranker?

MiniLM-L-6 crossencoder

Bi-encoders (used in FAISS) score query and
document independently. Cross-encoders see
both together — much higher accuracy for short
fact-check pairs.

Why not call LLM for
everything?

Tier 3 limited to 5-10%

At 5,000 posts/min, calling LLM for all would
cost thousands of dollars per day. The
confidence gate filters to only the genuinely
ambiguous cases.

Why Kafka over a
simple queue?

Kafka for production

Kafka persists messages, supports replay, and
scales to millions of messages. Simple queues
lose messages on crash. Use Redis Streams in
dev.

Why free MCPs over
paid?

DuckDuckGo +
Playwright + fetch

Google's Custom Search is closed to new
customers. Firecrawl requires a paid key. The
free stack handles all scraping needs with no
rate limits.

Why PostgreSQL +
pgvector?

Not a dedicated vector
DB

pgvector gives you vector search inside
PostgreSQL — ACID compliance, SQL joins,
versioned facts, and vector similarity in one
database. Simpler than running Pinecone or
Weaviate separately.
